# S3 methods: two ways a resume guard measured the wrong thing

**Found 2026-08-07**, while clearing the way for the S3 quantize-and-eval sweep and before
any of it was launched. Driver:
[`scripts/run_s3_allocate.py`](../../scripts/run_s3_allocate.py). Fixed in `b069794` and
`02f82b2`; guarded by ten tests in
[`tests/test_s3_reuse_guard.py`](../../tests/test_s3_reuse_guard.py).

## Why the guard exists at all

The S3 driver allocates six maps before it writes a single weight. Three of them are priced
from the channel moments, which costs about 1 h 45 m of CPU each on an 8B checkpoint — call
it seven hours before the GPU has anything to do. A run that already has the maps and only
wants the quantize and eval phases should not pay that again.

But the artifact this saves is the one every downstream number is a statement about, and the
failure mode of a resume guard is not that it declined to skip. It is that existence-on-disk
says nothing about *when* a file was written, so a map built from last week's signal gets
stapled into a fresh run and the table describes an allocation nobody asked for. That has
happened in this repository before, which is why `--reuse-maps` is off by default and why it
checks schema, model, group size, stats path, **allocator** and mtime rather than existence.

The allocator field is load-bearing in a way the others are not: `rank` and `dq` differ only
in whether a sensitivity table was passed, and both produce equally plausible integers. A
`dq` arm that reused the `rank` map would report the baseline's allocation under the
headline's name, at matched bytes, with nothing anomalous in the widths to notice.

## Defect 1 — freshness stamped against a file the run regenerates

The first version compared each map's mtime against the stats file the map *names*. For the
three signal arms that file is a **derived variant** — `dynquant_stats.signal.json` or
`dynquant_stats.shuffled-0.json` — which `write_variants` produces from S2's stats at the top
of every invocation, before any map is read.

So the comparison asked: *is this map older than a file I wrote thirty seconds ago?* Always
yes. The dry run said so plainly:

```
reusing map.rtn.json
rebuilding map.rank3.json: it predates an input it summarises
rebuilding map.shuf3.json: it predates an input it summarises
```

Five of six maps rebuilt. Only `rtn` survived, because it reads no stats at all. The guard
was not broken in the direction that loses data — it was refusing everything, which costs the
seven hours it was added to save while continuing to read at the call site as an
optimisation.

The fix is to stamp against the run's **sources** — S2's stats, S2's moments, and the merged
checkpoint — and not against its own intermediates. The variants keep their role as the
*identity* witness that separates `shuf3` from `dq3`, which is a different question and the
only one they can answer: the two name the same model, the same allocator and the same group
size, and differ solely in which variant priced them.

The general form: **a resume guard must compare against what it reads, not against what it
writes.** An intermediate regenerated by the same run carries no information about staleness,
however faithfully the artifact records having been built from it.

## Defect 2 — byte equality is not a content test for safetensors

Fixing defect 1 exposed a second one that had been hidden behind it. Both variants are a
deterministic function of the S2 stats and the seed, so they were routed through a
`_write_if_changed` helper that writes to a scratch file and keeps the original when the
bytes match. `arms.json` records the outcome as `rewritten`, and after defect 1 that flag is
the only thing in the run record that says a reused map was priced from the numbers now on
disk.

It was a constant `true`. Two consecutive full runs, on the box:

| artifact | run 1 | run 2 | size |
|---|---|---|---|
| `dynquant_stats.signal.json` | `62909acb…` | `62909acb…` | 87 839 |
| `dynquant_stats.shuffled-0.json` | `fdf89b2d…` | `fdf89b2d…` | 87 839 |
| `dynquant_moments.signal.safetensors` | `29521c95…` | `5798979e…` | 11 519 008 |
| `dynquant_moments.shuffled-0.safetensors` | `6d2b7012…` | `cbbdbf5e…` | 11 519 008 |

The JSON is byte-stable; the safetensors is not, at identical size. Two candidate
explanations — the values moved, or only their arrangement did — have opposite consequences
for whether the committed maps are still valid, so it was measured rather than assumed. Two
writes of the same in-memory object, in **one process**:

```
same process, two writes: c5973412170cba6c vs 70e08871ea657f90
key order identical:      True
same key set:             True (506 tensors)
tensors that differ:      0
observations match:       True
```

and, byte-wise:

```
header lengths: 66584 vs 66584   total: 11519008 vs 11519008
first differing byte: 43  (inside header: True)
payload identical:    True
header parses equal:  True
metadata equal:       True   entries: 254
metadata key order:   False
  first order split at index 0: 'obs:model.layers.8.mlp.down_proj' vs 'obs:model.layers.10.self_attn.v_proj'
```

`save_file` serialises `__metadata__` from a Rust hash map, and Rust seeds each map instance
separately, so the emission order differs between two calls in the same process. Nothing
numerical moved: 506 tensors, zero differing values, identical tensor key order, equal
observation counts.

The comparator now compares the payload and the *parsed* header, and the moments call sites
pass it explicitly. A comparison that is too strict does not fail safe here — it reports a
change on every run, and the flag stops distinguishing anything.

The general form: **`sha256(file)` is not a content identity for safetensors.** Any guard,
cache, dedup or provenance check built on the file hash will report a change every time and
read as working while distinguishing nothing.

## What the fixes are worth

Verified end-to-end on the box before the sweep was launched, at `02f82b2`:

```
shuffled control: 237/254 modules carry another module's measurements
  reusing map.rtn.json  … reusing map.dq4.json          (7 of 7)
  anchor 3b: widest drift rtn3 +0 B (0.00000%)
  anchor 4b: widest drift rtn4 +0 B (0.00000%)
rewritten: {'signal': False, 'shuffled': False}
```

All seven maps reused, both variants unchanged. Independently, the maps on the box are
sha256-identical to the seven committed under
[`experiments/phase3/s3_allocation/ministral-8b/maps/`](../../experiments/phase3/s3_allocation/ministral-8b/maps/)
— including `map.rank3.json`, which the aborted dry run rebuilt from scratch and which came
back byte-for-byte identical. That is a determinism check nobody designed, and it is the
strongest available evidence that the reused maps are the maps the reports describe.

## Guarded by

[`tests/test_s3_reuse_guard.py`](../../tests/test_s3_reuse_guard.py) — mostly negative, each
case wrong in exactly one way a finished map cannot be inspected for:

- a map older than S2's stats, and separately older than S2's moments, is rebuilt
- a map older than the merged checkpoint is rebuilt
- a map built by the other allocator is rebuilt
- a map naming another model, group size, or variant is rebuilt
- the flag is off by default
- **a map older than the derived variant it names is still reused** — the direct guard on
  defect 1, which would otherwise reappear as a plausible-looking tightening
- a safetensors file that only reordered its metadata is not a change, while a changed
  payload and changed metadata *values* both are
- both `save_moments` call sites pass the comparator that understands them — a correct
  comparator wired to nothing still reports every write as a change

Nothing downstream had run when these were found, so no reported number changes.
